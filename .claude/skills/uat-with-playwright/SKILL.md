# 受け入れ条件を Playwright で実画面確認する(UAT)

テスト(`sail test`)が通っていても、実際の画面で動くとは限らない。このスキルは、条件を**実ブラウザで1つずつ操作して**、判定と根拠を残す。**確かめて報告するだけ**で、アプリのコードもテストも直さない。

## 入力

確かめる受け入れ条件は、次のとおりです。

$ARGUMENTS

受け入れ条件そのものではなく、それが書いてあるファイルの場所を渡されたときは、
そのファイルを開いて、書かれている受け入れ条件を読んでから始めてください。

使うアカウント。指定がなければ CLAUDE.md の練習用アカウント（usera@example.com / userb@example.com、パスワード password）。

スクリーンショットの置き場所。指定がなければ作業ディレクトリ直下の uat-shots/。

## 準備

1. アプリが起動しているか確かめる。`curl -s -o /dev/null -w "%{http_code}" http://localhost/login` が 200 ならよい。落ちていれば `./vendor/bin/sail up -d` を提案する(勝手に起動しない)。
2. `uat-shots/` を作る(`mkdir -p`)。
3. Playwright のツールは deferred なので、`ToolSearch` で `select:` を使って先に読み込む(navigate・snapshot・take_screenshot・click・type・fill_form・evaluate・wait_for・close)。
4. 条件ごとに「どの画面で、何をして、何が見えれば満たすか」を、操作の前に頭の中で決めておく。

## 進め方

条件を**依頼の順に**確かめる。1つの条件につき、次を繰り返す。

1. 操作する。ログインやフォーム入力は、ページのスナップショット(`browser_snapshot`)で ref を確認してから行う。
2. **操作の結果が本当に起きたかを確かめる。** 送信なら画面が遷移したか・一覧が変わったか、`browser_network_requests` に POST が出たか。
3. 条件が満たされた(または満たされない)状態を、**フルページで**スクリーンショットに撮る。
4. 画面だけで分からないこと(DB に入ったか、消えたか、直接リクエストでも拒否されるか)は、次の方法で補う。
   - DB の中身: `./vendor/bin/sail artisan tinker --execute='echo json_encode(App\Models\Reply::select("id","post_id","user_id")->get());'` のように**読み取りだけ**する。DB への書き込みはしない。
   - 認可: ボタンが見えないだけでは足りない。ログイン中のページから `fetch` で `POST` + `_method=DELETE` + ページ内の `_token` を送り、**ステータスが 403 か**を確かめる。`redirect: 'manual'` を付ける。
5. 判定を決める。**画面に出ていないことを「満たす」の根拠にしない。** 例: 「エラーが出ていない」「リプライが増えていない」は、送信が実際に行われていなければ何の証拠にもならない。

### 他人との比較が要る条件(認可など)

- 作る側のユーザーでデータを作ってログアウトし、別ユーザーでログインして見る。
- ログアウトはヘッダーの「ログアウト」フォーム(`.logout-btn`)を使う。通常クリックが効かないときは 「通常のクリックが効かないとき」 と同じ扱いにする。
- どのユーザーで見ているかは、画面に出る表示名(投稿者名)で確かめる。ログイン後に `/posts/…` が開けたことだけで、誰として入っているかは分からない。

### 通常のクリックが効かないとき

このアプリでは、`browser_click` でフォームの送信ボタンを押しても送信されないことがあった(POST が出ず、画面も変わらず、入力した文字が残る)。ボタンが有効・重なりなし・JavaScript なしでも起きた。原因は未解明。

- **まず通常クリックで試す。** 効いたなら、それで進める。
- 効かなかったら(POST が出ない、画面が変わらない)、`browser_evaluate` でページ内から送信ボタンの `.click()` を呼ぶ。
  ```js
  () => { document.querySelector('form.reply-form button[type=submit]').click(); return 'clicked' }
  ```
  そのあと `browser_wait_for` で 2〜3 秒待ってから、状態を読む(タイトルが `Loading …` のままのことがある)。
- **この代替手段を使ったことは、報告に必ず書く。** どの操作でそうしたかも。実ブラウザで手で押したときに同じことが起きるかは、このスキルでは確かめられない、と書く。
- 通常クリックが効かなかった時点の画面は、「この結果を根拠にしない」と分かる名前で残してよい(例: `2-調査用-送信できない状態.png`)。

## スクリーンショット

- `browser_take_screenshot` の `filename` に `uat-shots/<行番号>-<何が分かる画像か>.png` を指定する。`fullPage: true` にする。
- **名前だけで、どの条件のどの場面か分かるようにする。** 同じ条件で複数枚撮るときは `4a-`, `4b-` のように枝番を付ける。日本語の名前でよい。
- 撮り直したら同じ名前で上書きする(古い失敗画像を条件の証拠として残さない)。
- fetch の 403 のように**画面に出ないもの**はスクリーンショットにならない。報告の文章でステータスを書き、画像はない、と明記する。
- 撮ったあとに `Read` で画像を開いて、写したい状態が写っているか確かめてよい(とくに「送信できたはず」の場面)。

## 後片付け

- 確認のために**画面から作ったデータは、画面から消す**(DB を直接書き換えない)。リプライを作ったら、そのユーザーの画面で削除して、元のデータだけが残る状態に戻す。
- 最後に DB を読み取りで確かめ、元から入っていたデータだけが残っていることを報告に書く。
- `browser_close` でブラウザを閉じる。
- `uat-shots/` と、Playwright が作る `.playwright-mcp/` は、コミットしない(依頼されたときだけ)。`.gitignore` に入れるかは、ユーザーに任せる。

## 報告の形式

条件ごとに1行ずつ、次の列の表で出す(Markdown の表)。

| # | 条件 | 判定 | 理由 | スクリーンショット |

- **判定は `満たす` / `満たさない` / `判定できない` の3つ**。条件つきなら `満たす(条件つき)` として、条件を理由に書く(例: 開いた時点でリプライが0件だった)。
- **理由は「何を操作して、何が見えたか」**を書く。DB や 403 など画面以外の根拠も、ここに書く。
- 複数枚・複数の根拠がある条件は、表の下に箇条書きで分けて書く。
- 表のあとに、次を必ず書く。
  - **通常クリックが効かず、代替手段を使った操作**(上記)。
  - **確かめていないこと**(実ブラウザで手で押した場合の挙動、他のブラウザ、モバイル幅など)。
  - **後片付けの結果**(消したデータ、残っているデータ)。
  - コミットしていないファイル(`uat-shots/`、`.playwright-mcp/`)。

## やらないこと

- アプリのコード・テスト・設計書を直さない。条件を満たさないときも、直さずに報告する。
- 画面で確かめていないことを「満たす」にしない。見ていないことは「見ていない」と書く。
- 依頼にない条件を勝手に足して判定しない。気づいたことは「気づいたこと」として別に書く。
- DB を書き換えない(読み取りだけ)。データの作成・削除は画面操作で行う。
