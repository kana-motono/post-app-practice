# PR差分を設計書と突き合わせてレビューする

差分を頭から順に読むと、設計書にない変更や「変えない」と約束した場所への変更が、大量の追加行に埋もれて見落とされる。そこで **「書いていないものが増えていないか」→「触っていないはずの場所」→「中身」** の順に読む。先に範囲のずれを押さえておけば、中身の指摘も「どこまでがこのPRの責任か」を分けて書ける。

このスキルは**読んで報告するだけ**で、コードも設計書も直さない。

## 入力

- PR番号(例: `2`)。指定がなければ聞く。
- 設計書のパス(例: `docs/reply.md`)。指定がなければ `docs/` を見て、PRの機能名に合うものを選ぶ。複数あって決められないときだけ聞く。

## 準備

1. 差分を保存して読む。長い差分は端末に流さず、スクラッチパッドのファイルに落としてから `Read` する。

   ```bash
   gh pr diff <N> > <スクラッチパッド>/pr<N>.diff
   ```

2. 設計書を全部読む。特に **「変えないもの」「スコープ外」「受け入れ条件」「テスト観点」** の節を使う。
3. このリポジトリの決まり(CLAUDE.md・`.claude/rules/testing.md`)は、書き方の揃いの基準に使う。ファイルを読まずに済むなら、すでに渡されている内容を使う。

## 手順

### 1. 設計書との突き合わせ — 書いていないものが増えていないか

- 設計書が無い機能のときは、そのイシューに書いた受け入れ条件を突き合わせ先にする。
- 差分に出てきた**ファイルを全部**挙げ、設計書のどこに書いてあるかを対応させる。対応先がないものが「設計書にない変更」。
- 逆に、設計書にあるのに差分に見えないものも挙げる(実装漏れか、別PRか、判断できない)。
- **依存まわりは必ず個別に確認する**: `composer.json`・`composer.lock`・`package.json`・`config/`・`.env*`。差分に含まれなければ「含まれない」と明記する(増えていないことも結果)。
- 「無修正で通る」「変えない」と書かれた既存テストが、差分で**変更されていないか**も見る。追加だけでも「無修正」とは言えないので、その旨を書く。
- 設計書自体が同じPRで追加されている場合は、「実装に合わせて書かれた可能性がある」と注記する。

### 2. 触っていないはずの場所

「変えないもの」の節と、既存の動きに関わるファイル(ルート・コントローラ・ポリシー・既存ビューなど)から、触っていないはずの場所を**4つ前後**選ぶ。依頼で指定されていればそれを使う。

- **消えた行(`-` で始まる行)から先に**読む。追加行より、消えた行のほうが既存の動きを壊しやすい。何が消え、何に置き換わったかを書く。
- そのあと追加行を読み、既存の動きと衝突しないか(ルートの順序、既存ボタンの出し分けなど)を確かめる。
- 差分に出てこないファイルは「差分に含まれない = 触っていない」と書く。
- **差分は「そのPRの時点」の姿**。PRより後に別PRがマージされていると、今のファイルは違う形になっている。`gh pr list --state merged` やマージ日時で前後関係を確かめ、今のファイルを読まないと判断できないときは、そう書く。

### 3. 中身

次の観点を、それぞれ1行以上で判定する。

| 観点 | 見ること |
|---|---|
| N+1 | 一覧・詳細で関連データを `with()` / `load()` で先読みしているか。ビューの `@can` などでクエリが増えていないか |
| 認可の置き場所 | コントローラの `authorize`・ポリシー・ビューの `@can` が揃っているか。ポリシーが自動検出されるか(`AuthServiceProvider::$policies` を触っていないか)。ポリシーのない操作は `auth` ミドルウェアだけで足りる設計か |
| マスアサインメント | `$fillable` の中身と、`create` / `update` に渡す値。`user_id` などをリクエストから読んでいないか |
| XSS | ユーザー入力が `{{ }}` で出ているか。`{!! !!}`、`style` や属性への埋め込みがないか |
| CSRF | フォームに `@csrf`(PUT/DELETE は `@method`)があり、ルートが `web` グループ内か |
| 入力チェック | ルール、日本語メッセージ、140字の数え方(CRLF→LF)、配列などの非文字列、空・空白のみ |
| 書き方の揃い | 既存コードとの重複・コピー、ビューの作り(共通レイアウトなし・インライン `<style>`)、テスト名・置き場所・ヘルパー、日本語のコメント |

テストは**差分の中身を読む**。テストが何を確かめていて、何を確かめていないか(例: 同時刻の並び、境界値、非文字列)を書く。テストを**実行したわけではない**ときは、実行していないと明記する。

## 報告の形式

観点ごとに1行ずつ、次の列で出す(Markdown の表)。

| 観点 | 判定 | ファイル:行 | 気づいたこと |

- **判定は `OK` / `要確認` / `対象外`/`判定できない` の4つ**。迷ったら `要確認` にして理由を書く。
- **判定できないとき**は、無理に `OK` にせず、判定欄に「判定できない」と書き、**何が足りないか**を書く(例: 今のファイルを読んでいない、テストを実行していない、差分に含まれない)。
- `対象外` は、そのPRの評価対象ではない理由を書く(例: 規則がPRより後に追加された)。
- 行番号は**差分の新しい側のファイルの行**。ハンクヘッダ(`@@ -a,b +c,d @@`)から数える。消えた行は旧行番号を `(旧N)` で添える。設計書の行は `docs/…md:N` で書く。
- 手順1・2・3の見出しごとに表を分ける。

最後に **「人が自分の目で読むべき場所」を3つまで**挙げる。選ぶ基準は、(a) 設計書にない変更、(b) 自動で確かめにくい判断(認可・入力の信頼境界)、(c) 出力のエスケープのように見落とすと被害が大きい場所。それぞれ**なぜそこか**を1文で添える。テストを回すと分かることがあれば、コマンドを1行で添える(`./vendor/bin/sail test`)。

## やらないこと

- コード・設計書・テストを直さない(指摘だけ)。
- 差分にない推測を事実として書かない。見ていないことは「見ていない」と書く。
- PRにコメントを投稿しない。依頼されたときだけ投稿する。
